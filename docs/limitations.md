# Ograniczenia i granice dowodu

Porównanie historycznych raportów bez skrótu tożsamości zwraca INCOMPARABLE. System plików musi obsługiwać hard linki; wynik zapisu dowodu nie gwarantuje, że plik nadal istnieje. Zapis Markdown i JSON nie jest jedną transakcją. Wsparcie workflow CI opisano w [instrukcji](ci-integration.md); lokalna weryfikacja nie potwierdza zdalnego uruchomienia GitHub Actions.

FaultLane v0.5 jest lokalnym narzędziem testowym. Nie monitoruje produkcji, nie wstrzykuje awarii do serwerów i nie publikuje danych. Paczka nie została opublikowana w npm. Weryfikacja tego wydania odbywa się na Windows/Node 24; Linux, macOS i pozostałe obsługiwane linie Node nie zostały tutaj przetestowane. Pełne reguły konfiguracji opisuje [przewodnik zgodności](real-world-compatibility.md).

1. **Browser routing nie przechwytuje fetch wykonywanego przez proces serwerowy Next.js.** Server Components, Server Actions, route handlers, zadania backendu, bazy danych i requesty spoza kontekstu Chromium wymagają innych mechanizmów. Lokalny backend może sam kontaktować się ze zdalną usługą; polityka przeglądarki tego nie blokuje.
2. PASS oznacza wykonanie zadeklarowanych requestów, symulacji i jawnych asercji UI w jednym przebiegu. Nie dowodzi pełnej odporności, poprawności biznesowej, dostępności zdalnego API ani przyczyny błędu. Mockowane 2xx potwierdza wyłącznie zachowanie klienta wobec syntetycznej odpowiedzi.
3. Strona aplikacji musi mieć origin HTTP(S) loopback: localhost, 127.0.0.0/8 albo ::1. Adresy LAN i zdalne strony są odrzucane. Nie ma flagi omijającej ten warunek ani wyłączania walidacji TLS. Przekierowania są odrzucane również pomiędzy lokalnymi adresami.
4. Legacy `api` zachowuje browser GET w originie aplikacji. Nowe `endpoints` obsługują fetch/XHR, dokładne originy i metody GET/HEAD/POST/PUT/PATCH/DELETE, pathname dokładne lub z końcowym `/*` oraz dokładne warunki query. Metody mutujące można wyłącznie mockować. Brak dopasowania po request body, dowolnego regex, CSS/XPath, eval, dynamicznych funkcji i automatycznego odkrywania usług.
5. Każdy cross-origin endpoint wymaga `mockOrigins`. Zgoda dotyczy przechwytywania, nie prawdziwego kontaktu z API. Forward jest dostępny tylko dla GET/HEAD w originie aplikacji lub jawnego dodatkowego originu loopback. Niedopasowane API są blokowane także same-origin. Reguły statycznych zasobów CDN są osobne i nie udzielają zgody na fetch/XHR do tych adresów.
6. Dozwolone dodatkowe zasoby są pobierane bez cookies i nagłówków autoryzacji przeglądarki, z limitem 8 MB i czasu, bez śledzenia przekierowań. Zasoby chronione sesją albo większe pliki wymagają innego lokalnego środowiska testowego. Zwykłe lokalne zasoby aplikacji, w tym pliki bundlera, pozostają dostępne.
7. Supabase-style REST oznacza GET kolekcji JSON pod `/rest/v1/...`, jawne filtry URL, syntetyczne tablice, podstawowe błędy 500/429 i nagłówki CORS/Content-Range. Nie oznacza testu wszystkich wersji SDK ani pełnej implementacji PostgREST. Nie są wspierane `.single()`, RPC, dynamiczna semantyka filtrów/paginacji, mutacje Supabase, Auth, Realtime, Storage ani bezpośredni PostgreSQL. Fixture używa fetch i syntetycznych nagłówków, bez SDK i prawdziwych kluczy.
8. Service workers są blokowane, a routing wyłącza HTTP cache. To świadoma zmiana środowiska: nie sprawdzamy zachowania offline, cache-first ani worker-controlled transport. Każdy scenariusz ma świeży kontekst, bez wcześniej zapisanej sesji i profilu. Brak przygotowania autoryzowanej sesji aplikacji przez zapisany storageState.
9. WebSocket i SSE nie są transportami objętymi symulacją. W nowym trybie WebSocket w originie aplikacji jest dozwolony dla HMR; inne są blokowane. Nie oznacza to izolacji od działań backendu ani kompletnej kontroli każdego kanału sieciowego przeglądarki. Testy wymagają kontrolowanego lokalnego środowiska z danymi syntetycznymi.
10. Odpowiedzi są buforowane. Slow jest kontrolowanym opóźnieniem przed mockiem lub lokalnym forward, nie modelem przepustowości. Oczekiwanie na sekwencję uwzględnia sumę wymaganych opóźnień plus `requestMs`, nadal podlegając całkowitemu `scenarioMs`. Asercja ładowania musi zajść jeszcze podczas wstrzykniętego opóźnienia, a nie wyłącznie podczas późniejszego pobierania. Sekwencja 429 potwierdza kolejne requesty i odpowiedzi; sama nie certyfikuje czasu backoff ani respektowania Retry-After przez aplikację.
11. Endpointy mają dokładne oczekiwane liczby requestów i twarde limity. Maksymalnie 10 endpointów, 30 requestów na endpoint i 30 odpowiedzi w sekwencji. Brak opcjonalnych endpointów oczekujących zera żądań. Równoczesne requesty dostają numery w kolejności obserwacji, nie zakończenia. Nie ma obietnicy powtarzalnej kolejności wyścigów po stronie aplikacji.
12. Legacy recovery wymaga jednego początkowego kliknięcia, jednego nowego prawdziwego 2xx i asercji. Nowe sekwencje mogą obejmować kilka requestów i automatyczne ponowienia. Każda wymagana odpowiedź musi rzeczywiście wystąpić. Nie dowodzimy pełnej przyczynowości względem ukrytych timerów aplikacji; po zamknięciu kontekstu nie ma dalszego monitoringu ani arbitralnego okna stabilności.
13. `waitForRequest.occurrence` jest liczone od początku scenariusza. Nie oznacza następnego requestu od chwili wykonania kroku. PASS wymaga całego planu; kroki po pierwszym błędzie są SKIPPED, nigdy zaliczone. Brak pierwszego przechwycenia to ERROR; brak kolejnego wymaganego requestu po awarii może być FAIL. Zablokowana nieplanowana zależność oznacza problem wiarygodności testu i ERROR.
14. Raporty nie zapisują query values, headers, cookies, request/response bodies, raw console logs, stack trace aplikacji ani wartości fill w opisach kroków. Zachowują origin/pathname, nazwy parametrów, metody, decyzje i liczniki. Ścieżki URL, nazwy i jawne oczekiwania mogą same zawierać poufne dane — konfiguracja pozostaje zaufana. Nie podawaj sekretów jako tekstów oczekiwań lub nazw endpointów.
15. Zrzuty obejmują widoczne dane strony i pola formularzy. Automatycznie maskowane są pola password i `data-faultlane-private`; można dodać `maskTestIds`. Nie jest to automatyczne rozpoznawanie wszystkich sekretów. Testuj dane syntetyczne. Nieudany wymagany zrzut po udanych asercjach zmienia PASS na ERROR; po zamknięciu przeglądarki z powodu timeoutu obraz może być niedostępny.
16. Metadane sieci zachowują pierwsze 200 zdarzeń; rekordy odpowiedzi są ograniczone do limitu endpointu plus jednej próby przekroczenia. Liczniki v3 obejmują późniejsze próby, bez przechowywania nieskończonego dziennika. Legacy zachowuje wcześniejsze nasycanie liczników do `maxRequests + 1`.
17. Konfiguracja `.ts` jest wykonywalnym zaufanym kodem. Zod waliduje wynik importu, nie bezpieczeństwo samego modułu. `--from-json` czyta jawnie wybrany lokalny plik o rozmiarze do 1 MB; nie uruchamia kodu JSON. Lokalny system plików pozostaje zaufany — ochrona ścieżek nie izoluje złośliwego procesu równolegle zmieniającego katalogi.
18. Doctor uruchamia Chromium, sprawdza schemat/politykę i lokalny origin/stronę, ale nie wysyła próbnych requestów do API i nie certyfikuje UI. Nie tworzy plików projektu; Chromium/tsx mogą używać katalogu tymczasowego. Kontrola uprawnień nie gwarantuje zapisu przy późniejszej zmianie ACL lub pełnym dysku.
19. Kreator nie odgaduje tekstów UI, portów ze złożonych skryptów ani gotowości hydratacji. SSR może pokazać przycisk przed podłączeniem handlera. Aplikacja powinna udostępniać gotowość przez disabled lub element dla waitForElement. Runner nie powtarza ukradkiem kliknięcia, aby uzyskać request.
20. Panel pozostaje lokalny, bez logowania. Czyta do 100 ostatnich raportów, waliduje Zod, zachowuje ochronę traversal/realpath i limity odczytu. Wersje 1/2/3 są czytane bez migracji; brakujące dane historyczne nie są wymyślane. Brak chmury, telemetrii, retencji, harmonogramów, płatności, wdrożeń i automatycznych poprawek. Własne workflow CI trzeba skonfigurować i uruchomić samodzielnie.
