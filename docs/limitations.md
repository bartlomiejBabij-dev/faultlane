# Ograniczenia i granice dowodu

v0.3 dodaje instalację i onboarding, bez rozszerzenia przechwytywania. Paczka jest lokalna i nie została opublikowana. Automatyczna weryfikacja instalacji odbywa się na Windows/Node 24; macOS, Linux i inne obsługiwane linie Node wymagają własnego sprawdzenia. Implementacja używa przenośnych API Node, bez powłoki w runtime CLI.

Doctor uruchamia przeglądarkę, wykonuje GET originu i strony, lecz nie testuje UI ani API. Kontrola uprawnień nie gwarantuje przyszłego zapisu przy pełnym dysku lub zmienionych ACL; dopiero run weryfikuje dowody. Doctor nie tworzy plików w projekcie, ale Chromium/tsx korzystają z systemowego katalogu tymczasowego. Zaufana konfiguracja `.ts` może sama wykonywać kod — to granica zaufania, nie gwarancja braku skutków ubocznych dowolnego pliku.

Kreator nie wykrywa endpointów, tekstów UI, gotowości hydratacji ani portu ze złożonych skryptów. Wymaga danych użytkownika. Slow ma jawną asercję ładowania, empty nadal zwraca `[]`. SSR może pokazać przycisk przed handlerem; aplikacja powinna udostępniać gotowość przez disabled lub element dla waitForElement. Runner nie powtarza potajemnie kliknięć w celu uzyskania requestu.

1. **Playwright browser request interception nie obejmuje automatycznie API wywoływanego wewnętrznie przez kod serwerowy Next.js.** Server Components, Server Actions, backendowe zadania i połączenia do baz wymagają innych mechanizmów testowania. Demo celowo używa fetch w komponencie klienckim.
2. PASS oznacza tylko spełnienie jawnych oczekiwań w jednym wykonaniu. Nie dowodzi pełnej odporności, dostępności, poprawności biznesowej, wydajności ani przyczyny błędu. Błędny kontrakt testowy może opisywać niewłaściwe zachowanie.
3. Tylko Chromium i browser GET w originie `baseUrl`, wyzwalany nawigacją albo deklaratywnym krokiem. Brak logowania, zachowanego profilu, mutujących API, GraphQL POST, SSE i wstrzykiwania usterek WebSocket. Lokatory mają jawny podzbiór ról ARIA; brak CSS/XPath, eval i dowolnego JavaScript. `count` sprawdza liczbę w DOM, nie widoczność.
4. Tylko `localhost`, IPv4 127.0.0.0/8 i IPv6 `::1`. Adresy LAN oraz zewnętrzne są odrzucane; nie ma flagi obejścia. Zewnętrzne zasoby i metody inne niż GET/HEAD są blokowane. Przekierowania są odrzucane w całości, także lokalne łańcuchy; skonfiguruj URL docelowy. Baseline korzysta z tych samych reguł sieciowych co awarie.
5. Loopback nie gwarantuje, że backend jest bezpieczny: lokalny proxy może wywoływać usługi zewnętrzne, a źle zaprojektowany GET może zmieniać dane. Uruchamiaj tylko własne środowisko developerskie z syntetycznymi danymi i bez połączenia z produkcyjną bazą. FaultLane nie zmienia konfiguracji backendu.
6. Odpowiedzi przepuszczane przez `route.fetch`/`fulfill` są buforowane. MVP nie odtwarza precyzyjnie streamingu ani czasu sieci produkcyjnej. „Slow” to kontrolowane opóźnienie przed prawdziwym żądaniem, a nie model przepustowości. Nie testuje respektowania Retry-After ani automatycznych retry/backoff; sprawdza skonfigurowany komunikat.
7. Service Workers są blokowane, konteksty są nowe. Aplikacje zależne od istniejącej sesji lub offline cache wymagają rozszerzenia konfiguracji. Lokalne WebSockety są przepuszczane dla HMR, lecz nie są izolowane od lokalnego backendu jako kanał aplikacyjny.
8. Dane raportu nie obejmują nagłówków autoryzacji, cookies, request bodies, pełnych logów konsoli, surowych wyjątków, query URL strony i wartości fill w opisie kroków. Teksty oczekiwań/nazwy pochodzą z zaufanej konfiguracji. Zrzut obejmuje widoczne dane strony, także wypełnione pola: oznacz prywatne fragmenty `data-faultlane-private` lub dodaj `maskTestIds`. Maskowanie nie rozpoznaje automatycznie wszystkich sekretów.
9. Zrzut jest najlepszą próbą w przypadku awarii przeglądarki. Przekroczenie globalnego limitu zamyka kontekst; raport wtedy może nie mieć obrazu. Nieudany wymagany zrzut po udanych asercjach zmienia PASS na ERROR.
10. Panel jest lokalny i nie ma logowania. Serwer domyślnie wiąże się z loopback. Nie publikuj panelu. Czyta maksymalnie 100 ostatnich katalogów uruchomień, waliduje JSON, pomija uszkodzone/nieukończone raporty i ogranicza rozmiar odczytu. Chroni przed traversal i typowym symlink escape, ale nie przed złośliwym lokalnym procesem ścigającym się z odczytem systemu plików.
11. Konfiguracja `.ts` jest wykonywana przez `tsx`; Zod waliduje dane po imporcie, a nie bezpieczeństwo kodu. Używaj tylko zaufanych konfiguracji. Katalog raportów i dane na dysku są lokalną odpowiedzialnością użytkownika.
12. Brak retencji, harmonogramu, monitoringu produkcyjnego, kolejki, integracji CI, usług płatności, kont użytkowników, AI API i automatycznych poprawek. Raporty v1 są czytane bez migracji; brakujące nowe pola nie są uzupełniane fikcyjnymi danymi.
13. Recovery wymaga jednego początkowego click, a potem tylko oczekiwań/asercji. Nie obsługuje wieloetapowych formularzy odzyskania, wielu endpointów naraz ani rozgałęzień. Jedna konfiguracja nadal ma maksymalnie jeden scenariusz każdego typu awarii; warianty można zapisać w osobnych plikach.
14. `waitForRequest.occurrence` jest liczone od początku scenariusza i nie oznacza „następnego requestu od chwili wykonania kroku”. Dzięki temu szybkie żądania nie giną. Recovery ma dodatkową weryfikację nowego requestu po click, niezależną od tej akcji.
15. Kontrakt recovery obejmuje zaobserwowane żądania w czasie testu, nie dowodzi pełnej przyczynowości. Ukryty timer uruchomiony po kliknięciu może być nierozróżnialny od handlera click. Żądania przed Retry, nadmiarowe requesty podczas testu i sukces UI bez nowego requestu są wykrywane. Po zamknięciu kontekstu nie ma dalszego monitoringu ani arbitralnego „okna stabilności”.
16. Liczniki i rekordy są ograniczone do `maxRequests + 1`; po przekroczeniu limitu requesty są blokowane i liczba jest nasycona. Nie jest to dokładny profil całej nieskończonej pętli. Kroki po pierwszym FAIL/ERROR są SKIPPED, co skraca wykonanie bez ukrywania niesprawdzonych oczekiwań.
